# Accepted decisions

| ID | Decision | Reason and effect |
| --- | --- | --- |
| ADR-001 | PREPARATION until explicit onsite unlock | No product code, model definitions, unapproved trained weights, schema scripts or executable tests before onsite. The narrow local-artifact exceptions are ADR-018 and ADR-021. |
| ADR-002 | Every audited feature remains required | Scheduling risk is reported, not resolved by silently deleting scope. |
| ADR-003 | Final frontend is visual and interaction authority | Reconstruct approved layouts and flows onsite without a redesign. |
| ADR-004 | One Next.js client and one Azure VPS | Public and portal share server-owned data and HTTPS origin. No separate hosted showcase. |
| ADR-005 | Immediate scrimmage finalization | User selected one authorized participating leader's valid submission; remove confirmation timers and finalizer service. First committed result wins; conflicting later writes return 409. |
| ADR-006 | Fresh database schema | PCC begins with fresh onsite migrations; no external migration history is an upgrade path. |
| ADR-007 | One authoritative linked wallet per user | Store on users; profile projects it read-only. Duplicate addresses across users remain permitted; verify each user's linking independently. |
| ADR-008 | Finalized data is server-owned | Client local state only covers draft forms, navigation and display preferences, not identity or official results. |
| ADR-009 | No fabricated biometric/provider success | Missing dependencies return unavailable; OCR remains draft until authorized review; chain/provider actions need evidence. |
| ADR-010 | Plain prose/table contracts | No SQL, Python, TS, Rust, generated OpenAPI or executable test implementations in docs. |
| ADR-011 | Approved non-code assets and reference datasets transfer | Preserve attribution and checksums; no private records or trained weights except the narrowly controlled local artifacts in ADR-018 and ADR-021. |
| ADR-012 | PostgreSQL is durable event authority | Outbox records persist notifications/provider work; Redis carries transient delivery only. |
| ADR-013 | Exact amounts | PHP centavos and SOL lamports are canonical; decimals are formatted strings at UI boundaries. |
| ADR-014 | Public invitation-only tournaments remain discoverable | PRIVATE means registration requires a code, not hidden tournament discovery. |
| ADR-015 | Selective shadcn/ui primitive foundation | After onsite authorization, use a version-pinned shadcn/ui Base UI foundation for specified accessible primitives only; PCC custom components own the approved visual system. Do not bulk-install the registry or substitute default shadcn styling for the preserved interface. |
| ADR-016 | Fast-feedback frontend validation at the hackathon | Use focused unit, API/integration and Vitest component tests where they protect changed behavior. Do not spend hackathon time creating or running automated browser E2E/visual-regression suites; developers instead report the manually checked routes, states, widths and keyboard behavior. |
| ADR-017 | Staging-gated configured hackathon demo OTP | The user-authorized, non-secret `PCC_HACKATHON_DEMO_OTP_CODE=123456` is accepted only when exact staging mode and `PCC_HACKATHON_DEMO_OTP_ENABLED=true` are both present. It creates auditable `DEMO_BYPASS` access, never fabricated email/provider/biometric/wallet/settlement evidence, and does not alter immediate atomic scrimmage-result finalization. |
| ADR-018 | Manual W600K-R50 face-model artifact | The user authorized one local face-embedding ONNX artifact at `models/face-recognition/w600k_r50.onnx`. It remains Git-ignored and is manually provisioned and SHA-256-verified on every development machine and the staging VPS. It is read-only to the biometric runtime, never copied into an image, bundle, browser response or object store. Missing or mismatched bytes make biometric operations unavailable without a verification write; every other model/weight remains excluded during preparation. See [face-model record](FACE_RECOGNITION_MODEL.md). |
| ADR-019 | InsightFace embedding is paired with Human browser blink capture | W600K-R50 is an InsightFace ArcFace embedding model, not a face detector or liveness model. The version-pinned frontend `@vladmandic/human` 3.3.6 pipeline owns face detection, multiple-face rejection, landmark alignment, crop generation and the server-prompted blink/liveness/anti-spoof capture gate; the backend must not repeat face detection or counting. PCC enables biometrics only with the documented InsightFace-use record, reviewed locally served Human assets and matching capture policy. A server-issued, single-use challenge binds the session, purpose and server-computed crop digest, preventing simple replay/cross-scope use, but the Human browser result is not cryptographic or independently server-verifiable proof. Do not claim high-assurance identity/liveness, fabricate a browser result, or add a liveness provider merely for implementation convenience. Missing/mismatched inputs return unavailable without a write. |
| ADR-020 | Exact, serialized biometric duplicate decision | A transaction-scoped enrollment lock serializes every enrollment. The database performs the final compatible-model/preprocessing vector comparison inside that transaction; an approximate pgvector index may narrow candidates but can never be the final duplicate decision. A duplicate result is a generic conflict and never identifies or scores another person. |
| ADR-021 | Manual RF-DETR MLBB-layout artifact and local-only extraction | The user authorized the RF-DETR Medium checkpoint at `models/scoreboard/roboflow_weights.pt` for a detector-led MLBB post-match pipeline. It remains Git-ignored, is manually provisioned and SHA-256-verified on every development machine and the staging VPS, and is mounted read-only into the worker—not copied into an image, bundle, browser response or object store. The pipeline is RF-DETR layout detection, recognition-only local PaddleOCR on detector crops, and checksum-pinned local hero-template ranking. There is no external screenshot/model-provider fallback. Candidate ranks, fuzzy identity suggestions and unreadable fields remain review data; only an authorized reviewer can atomically accept official game data. Missing/mismatched runtime inputs leave extraction unavailable and manual entry explicitly manual. See [MLBB extraction](MLBB_SCOREBOARD_EXTRACTION.md). |
| ADR-022 | Bounded, fixed-layout MLBB screenshot intake | The extractor supports only `mlbb_post_match_v1`. It accepts no more than 10 MiB, 16,777,216 decoded pixels and 8192 pixels on either side; it normalizes EXIF orientation in memory, removes metadata from the processing image and bounds decode to five seconds. Valid media that cannot attest the fixed layout remains `NEEDS_REVIEW` with `UNSUPPORTED_LAYOUT`, without inferred fields or automatic retry against another layout. Future MLBB UI/hero/skin/catalog expansion is outside this hackathon unless explicitly authorized. |
| ADR-023 | PayMongo test-mode Hosted Checkout only | The hackathon may use PayMongo's `sk_test_` test mode to demonstrate an entry-fee lifecycle through backend-created Hosted Checkout v2 sessions. Test-mode checkout is not real collection. Redirects never settle; raw signed test webhooks plus provider-resource reconciliation bind exact PHP-centavo snapshots to an internal attempt before an atomic registration transition. Live keys/events, refunds, recipient onboarding, Wallet/disbursement/payout flows, InstaPay/PESONet, payment splitting and PayMongo prize settlement are unavailable. See [PayMongo readiness](PAYMONGO.md). |
| ADR-024 | Fresh Devnet-only Solana evidence and individually immutable Core certificates | PCC never reuses an externally supplied signer, program ID, collection, metadata URI, transaction, IDL or Devnet deployment. Every enabled chain path is locked to Devnet cluster/genesis and finalized evidence. Browser wallets sign only their own wallet-link, entry, or creator-funding action; an isolated worker signer handles operator release and certificate issuance. Official certificates are individually frozen Metaplex Core assets with update authority `None`, not Token Metadata NFTs or a false collection-membership claim. See [Solana readiness](SOLANA.md). |
| ADR-025 | Soulbound Core NFT certificate evidence, public metadata and registry voiding | A PCC certificate is a Metaplex Core NFT asset, not a legacy Token Metadata mint. Its standard public label is `Core asset address`. The worker creates its asset-level `PermanentFreezeDelegate` with `frozen: true` and authority `None`, then removes update authority; a named freeze delegate is rejected because it could thaw. Only server-derived `pcc-certificate-v1` public metadata and a reviewed static image leave PCC. Submission ambiguity is `PENDING_RECONCILIATION` and is reconciled against the original candidate, never by a replacement signature. `VOIDED` is a PCC public-registry state with retained evidence, not an on-chain mutation. See [Solana readiness](SOLANA.md) and [certificate issuance runbook](runbooks/SOLANA_CERTIFICATE_ISSUANCE.md). |
| ADR-026 | Staging OpenAPI is available by default | The user directs `PCC_OPENAPI_EXPOSED=true` for hackathon staging. The published contract must remain free of secrets, private examples, internal host paths, provider diagnostics and non-public schemas; a malformed value stops startup. |

## PCC design safeguards

| Safeguard | PCC target |
| --- | --- |
| Persistent notifications | Persist recipient read/dismiss state. |
| Community and tournament presentation | Specify full frontend-supported persistence before coding. |
| Biometric verification | Reject/unavailable with no verified mutation when evidence is absent. |
| Authorization | Derive actor from verified session. |
| Wallet and analytics | Project the authoritative wallet and calculate canonical statistics. |
| Scrimmage results | Immediate atomic finalization with no scheduled finalizer. |
| Brand motion | Preserve approved static assets and specify motion for onsite recreation. |

## Unresolved external facts

VPS hostname/capacity and provider entitlements are not yet supplied. They are deployment prerequisites, not reasons to omit specifications. No official event-rule compliance certification is implied. Team/event timing comes from the user's accepted schedule.
