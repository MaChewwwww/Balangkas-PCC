# Identity, authorization and privacy contracts

| Concern | Required behavior |
| --- | --- |
| Session | Short-lived signed session JWT in Secure HttpOnly SameSite=Lax cookie, 24-hour expiry; session row enables logout/revocation. No bearer token in localStorage. |
| CSRF | Require same-origin Origin and session-bound CSRF token on cookie-authenticated mutations. WebSocket upgrade verifies session and Origin. |
| Password | Argon2id hash; minimum 12 characters, maximum 128; never log credentials. Password reset token single-use, 15-minute expiry, hashed at rest. |
| OTP | Six digits, 10-minute expiry, 5 attempts; 60-second resend interval, 5 sends per hour per account/IP. Generic request response avoids account enumeration. |
| Hackathon staging demo OTP | The committed non-secret `PCC_HACKATHON_DEMO_OTP_CODE=123456` is accepted only with `PCC_ENVIRONMENT=staging` and `PCC_HACKATHON_DEMO_OTP_ENABLED=true`. It creates `DEMO_BYPASS`, logs a non-secret audit event, never sets `email_verified_at` or any provider/biometric/wallet/settlement evidence, and its sessions are rejected when the flag is disabled. Missing or altered code configuration leaves the bypass unavailable. |
| Local auth fixtures | The ignored `.env.accounts` catalog is development-only and uses the reserved `auth.seed.balangkas.invalid` domain. A fixture session is explicitly `SEED_FIXTURE`, never sets `email_verified_at` or external evidence, and is rejected/revoked in staging or production. Reserved-domain signup by a non-fixture path is invalid; an existing non-fixture account can never be overwritten by a seed run. |
| Browser origin | Same-origin application/API on the VPS; CORS is disabled by default. Any separately approved first-party origin must be exact, never `*`, and must preserve CSRF/Origin checks. |
| Public API docs | The user-authorized hackathon staging default exposes OpenAPI/docs. Published output must never disclose secrets, private examples, internal host paths, provider diagnostics or schemas that are not safe for public contract publication. |
| Resource ownership | Use session user ID. Client owner/creator/user fields cannot grant permissions. Per-resource role checks on every write. |
| Portal navigation context | Treat every `from*`/`from` query value as untrusted presentation input. Resolve the destination first through the session, then return only relation-proven, permission-filtered ancestors under [the breadcrumb-context contract](screens/BREADCRUMB_CONTEXT.md). A context value cannot trigger a parent-only fetch, reveal a title/link, select a hidden resource or authorize an action. |
| Biometric input | Consent plus a server-issued, single-use Human blink challenge precede one JPEG/PNG/WebP crop (2 MiB, 4,194,304 decoded pixels). The version-pinned frontend `@vladmandic/human` pipeline detects exactly one face, rejects multiple faces, aligns it, runs the blink/liveness/anti-spoof capture gate and creates the crop. The server byte-caps and decodes it in memory but does not repeat face detection or counting. |
| Browser liveness capture | The server binds a Human blink challenge to the session user, requested action/resource, expected package/policy identity and short expiry. It consumes the challenge only with a structurally valid matching browser report and its own digest of the submitted crop. Replayed, expired, cross-user, cross-resource, cross-policy or cross-crop requests are rejected without a biometric write or authorization. This does not establish cryptographic or independently server-verifiable liveness: Human is a client-side hackathon capture control, so the UI and audit language must not overclaim it. Missing reviewed Human assets or policy means unavailable. |
| Face model artifact | Only the hash-verified W600K-R50 artifact in [the face-model record](FACE_RECOGNITION_MODEL.md) may be used. It is manually provisioned per machine, mounted read-only into the biometric runtime, and is never in Git, an image layer, browser response or object store. |
| Enrollment | Normalize the 512-d embedding only after the frontend Human capture gate, challenge/crop binding and reviewed capture policy pass. A transaction-scoped enrollment lock serializes the final exact comparison for the same model hash and preprocessing version; pgvector approximate search is candidate-only. Similarity >= 0.65 is a generic duplicate conflict. Missing/mismatched model, absent use approval/Human asset or policy, inference failure or invalid frame cannot create a successful biometric enrollment. |
| Duplicate privacy | Return `409 BIOMETRIC_DUPLICATE` without matched user ID, similarity, embedding, detector/liveness output or whether another account exists. Audit only the non-sensitive reason/category. |
| Wallet link/change | Single-use signed wallet challenge + a fresh 1:1 biometric similarity >= 0.70 verified against the caller's current enrollment; five-minute biometric authorization expiry. The authorization is bound to the user, wallet-link action and challenge; atomic update of users.linked_wallet_address with audit. Wallet sharing across users is permitted. |
| Solana Devnet | Exact `PCC_SOLANA_DEVNET_ONLY=true`, configured Devnet cluster/genesis and finalized RPC evidence are mandatory. Browser signs only server-snapshotted message/entry/funding transactions; worker-only read-only signer handles certificate/escrow operator actions. Verify canonical public keys, exact lamports/memo/destination, transaction success and finalized state. Never accept a browser callback as payment/funding/issue proof, expose a signer, use Mainnet/Testnet, or retain raw transaction/keypair bytes. |
| Certificate metadata | Only server-derived `pcc-certificate-v1` public metadata and approved static image can leave PCC for the configured permanent Devnet store. Persist metadata/image URI/SHA-256/provider reference and independent public-read evidence; never upload email, UUID, raw wallet address, biometric/audit data, signer paths, private void notes or secrets. Issue only after finalized Metaplex Core NFT asset owner/URI/hash/`PermanentFreezeDelegate(frozen: true, authority: None)`/no-collection/no-update-authority verification. |
| PayMongo test checkout | Only `sk_test_` server credentials and `livemode=false` events are accepted. Create Hosted Checkout server-side from the immutable registration snapshot; card/bank/e-wallet details never enter PCC. Verify `Paymongo-Signature` as HMAC-SHA256 over raw request bytes using timing-safe comparison before parsing, record only sanitized identifiers/status/amount/currency, de-duplicate the event, then reconcile the expected Checkout Session/payment server-side. Redirects/query parameters and client state cannot mark `PAID`. Live keys/events and Wallet, recipient, payout, transfer, InstaPay/PESONet, refund and dispute operations are unavailable. |
| Tournament entry | Leader supplies a fresh five-minute single-use biometric authorization bound to the user, registration action and exact tournament. No client-generated proof or authorization reuse. |
| Face retention | Delete raw face bytes after inference or rejection; never send them to object storage, logs, backups or provider payloads. Persist only the embedding, consent, model/preprocessing/frontend-capture-pipeline/liveness identities and non-sensitive audit data. Do not expose embeddings or verification internals publicly. |
| Object privacy | Authorize evidence/lobby access before response; no public object listing. Remove metadata from user image uploads. |
| Codes | Store team/community/tournament invite hashes only; reveal fresh code once to authorized creator, then rotate if lost. Directory never exposes codes. |
| Logs | Correlation IDs and non-sensitive event references; no tokens, face bytes, lobby passwords, invite codes or payment-account details. |

## Role matrix

| Resource/action | Visitor | Member/player | Leader/manager | Creator/operator |
| --- | --- | --- | --- | --- |
| Public directory | Visible records only | Same public policy | Same public policy | Same public policy |
| Own profile/wallet | No | Own only | Own only | Cannot bypass recipient proof |
| Team private details | No | Active member | Captain/coach/manager | Team captain controls delegation |
| Team settings/archive | No | No | Captain or delegated manager | Historical records retained |
| Community posts | No | Active community member | Owner/manager moderate | Owner manages access/archive |
| Tournament settings/staff | No | No | Assigned staff read/operate allowed match views | Creator only; staffing locked after start |
| Official tournament result | No | Read permitted projection | Explicit tournament match-review permission | Creator permitted |
| Scrimmage result | No | No | Participating team captain or manager | No unrelated global-user bypass |
| Payout release | No | No | No | Authorized operator after readiness and immutable allocation |
| Certificates | Issued public record only | Own credential view | No implicit signer access | Authorized tournament issuer |

Private player details are available to self and authorized competition operations only; public profile navigation never substitutes a different player when an ID is missing. Return 404 for hidden records, 403 for an authenticated visible resource's forbidden action.
